# План API (ещё не реализован)

Фронтенд вызывает только российский публичный фасад (Yandex API Gateway + Cloud Function). Укажите его URL в `assets/config.js`; адрес `workers.dev` не используйте как публичный endpoint.

## Публичные маршруты

- `GET /slots?date=YYYY-MM-DD&service=slug` → `{ "slots": ["10:00", "14:00"] }`
- `GET /schedule.json`, `GET /busy`
- `POST /book` принимает `service`, `date`, `slot`, `name`, `phone`, `consent` и возвращает только после фактического создания: `{ "ok": true, "id": "…", "start": "…", "end": "…" }`.

Расписание и записи, включая контактные данные, должны храниться в российской базе с транзакциями. Выбор конкретного сервиса и схема пока не реализованы. Проверка свободного окна и создание записи выполняются атомарно, чтобы исключить двойную запись. Для повторов после таймаута нужен ключ идемпотентности: повторный запрос не создаёт дубликат.

Фото при необходимости хранятся в отдельном закрытом российском Object Storage. Публичный бакет сайта не содержит клиентских данных. Доступ к `/pd/*` и планеру требует серверной авторизации; ключи хранятся исключительно в секретах окружения.

Уведомления TG/MAX отправляются из очереди после сохранения записи и повторяются при сбое. Ошибка мессенджера не отменяет запись. Cloudflare допускается только как вспомогательный компонент для ботов; приём и чтение записей не должны от него зависеть. Поля `client_chat` и другие идентификаторы пользователя также остаются в российском контуре.

## Проверки перед релизом

1. Проверить CORS и OPTIONS для каждого публичного маршрута с домена сайта.
2. Проверить, что неуспешная запись, таймаут или некорректный JSON никогда не получают `ok: true` на клиенте.
3. Проверить российскую базу, конкурентное бронирование, идемпотентные повторы, TG/MAX-уведомления, отмену, планер и `/diag` под админ-авторизацией.
4. Не логировать запрос `POST /book` целиком и не добавлять ПДн в аналитику.

Текст для уведомления в реестр операторов ПДн и финальная политика требуют заполнения ФИО, ИНН, адреса и контакта самозанятой.
