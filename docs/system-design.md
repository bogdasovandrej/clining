# Как будет работать сервис: предложение для согласования

Обновлено 20.09.2026 после вопроса Андрея о необходимости планера.

## Рекомендация

Для одной выездной специалистки полноценный календарный планер не обязателен к первому запуску. Начинаем с заявки на оценку и ручного подтверждения времени. Длительность генеральной уборки и дорога между адресами плохо укладываются в фиксированные слоты без предварительного разговора.

Два пользовательских сценария:

1. Клиент выбирает услугу → видит стартовую цену → оставляет телефон и желаемую дату → получает номер сохранённой заявки → поддерживающая уборка оценивается по фото, генеральная и послестроительная — после предварительного осмотра → мастер согласует цену, адрес и время → подтверждает визит и добавляет его в календарь.
2. Клиент сразу пишет в Telegram/MAX и отправляет фото → мастер оценивает задачу → фиксирует договорённость в том же списке заявок. В первом релизе это может быть ручное добавление; автоматический приём фото ботом — следующий этап.

Пока боты не созданы, опубликованный макет предлагает звонок по рабочему номеру. Ссылки TG/MAX не подменяем вымышленными аккаунтами. После создания ботов оба канала получают одну и ту же сохранённую заявку; база остаётся источником истины.

Заявка становится подтверждённой записью только после согласования. Сообщение «Заявка получена» допустимо после реального сохранения; сообщение «Вы записаны» — после подтверждения визита. При таймауте нельзя утверждать, что запись точно не создана: повтор должен использовать тот же идентификатор запроса и возвращать прежний результат.

## Что видит мастер

Новая заявка приходит уведомлением. Основные действия: назначить оценку по фото или осмотр, указать согласованную цену/время, подтвердить с добавлением в календарь, перенести, отменить, завершить. Нужен один список с фильтрами «новые / оценка / подтверждены / завершены / отменены». Точная форма управления — мастер-бот и/или небольшая закрытая страница — зависит от выбранного календаря. Это не отдельная большая CRM.

Полноценный планер с календарной сеткой имеет смысл при нескольких мастерах, большом количестве пересекающихся выездов или явном запросе заказчицы. ICS, блокнот, управление графиком через сложный бот и клиентские боты остаются в бэклоге; их необходимость обсуждается после первых заказов.

## Где хранится информация

- Сайт и его файлы: Yandex Object Storage, Россия.
- API: российская Cloud Function через API Gateway.
- Единая база в РФ: заявка, контакт, согласие, цена, адрес, статус и согласованное время. База поддерживает транзакции для исключения пересекающихся подтверждённых выездов.
- Фотографии: отдельное закрытое российское хранилище, если появится загрузка на сайте. В сегодняшнем макете загрузки нет.
- Уведомления: после сохранения заявка отправляется одновременно в Telegram и MAX через отдельную очередь. Сбой одного канала не отменяет запись и не мешает повтору доставки. В сообщении по умолчанию только номер заявки, услуга и ссылка на авторизованный просмотр; объём передаваемых персональных данных уточняем отдельно.
- Клиенту нельзя обещать сообщение бота только по введённому телефону: подключение канала должно быть отдельным явным шагом. До этого мастер отвечает по согласованному доступному каналу.

Вывод — проектное решение, а не утверждение о внутренней архитектуре конкурентов: первому релизу достаточно надёжного сбора и учёта заявок. Масштабный планер сам по себе не улучшит работу, если заказчице удобнее подтверждать выезды лично.

## Что уточнить перед реализацией

Один мастер или несколько; число выездов в день; текущий способ ведения записей; нужен ли автоматический выбор свободного времени; где удобнее подтверждать заявки. До ответа сегодняшний макет показывает **желаемую дату**, без выдуманного расписания свободных слотов.
